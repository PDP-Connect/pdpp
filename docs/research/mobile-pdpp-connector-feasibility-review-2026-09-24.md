# Independent review: Mobile / PDPP connector feasibility

**Date:** 2026-09-24
**Disposition:** Accept the rejection of B as a direct Mobile runtime. Revise A into a bounded experiment, not a committed shared-implementation migration. The accompanying assessment incorporates these corrections. No P0 finding. This is a read-only source review; no device run or Personal Server acceptance test was performed.

## Findings

### P1 — Meta sharing is materially less feasible than the memo's “medium-high” rating

The memo recommends a Meta dual-target pilot in [decision, lines 57–63 and 77](mobile-pdpp-connector-feasibility-2026-09-24.md), but its current collector is mostly browser orchestration: session-cookie inspection, `page.evaluate`, navigation races with `waitForResponse`, scrolling, Accounts Center DOM interaction, and Playwright handoff. See [`connectors/meta/index.ts`](</home/tnunamak/code/data-connectors/connectors/meta/index.ts>) lines 123–135, 164–265, 299–419, 472–545, 604–779, and 779–919. Mobile's PageShim offers related but different `captureNetwork`/`getCapturedResponse` primitives ([`page_shim.dart`](</home/tnunamak/code/unity-surfaces/apps/mobile-shell/lib/connect/page_shim.dart>) lines 513–543, 1202–1243), and the legacy script implements a separate collection flow ([`instagram-2.2.1.js`](</home/tnunamak/code/unity-surfaces/apps/mobile/public/connectors/instagram-2.2.1.js>) lines 611–804). The reusable part is chiefly pure parsing, record normalization, schemas, and provider constants. Even `parsers.ts` imports `node:crypto` for an ID hash ([line 8](</home/tnunamak/code/data-connectors/connectors/meta/parsers.ts:8>)), so it is not currently a Mobile bundle as-is. A large common browser facade could merely relocate two incompatible event and session models.

**Correction:** Make shared pure parsers/record builders the initial extraction. Implement separate host collection loops. Count reuse only after a fixture and device proof shows the same raw provider responses produce equivalent stream records, including empty, partial, pagination, login, and error outcomes. Choose a simpler connector if the aim is to prove a general build pattern; retain Meta as a hard compatibility test. Confidence: high on the coupling, medium on the ultimate extraction cost.

### P1 — The proposed Meta declaration and scope mapping cannot be admitted by today's Unity PDPP path

The memo's step 2 suggests pinning a Meta profile and declaration, and step 4 suggests adapting `buildCollectionProfileEnvelopes` ([decision, lines 76–79](mobile-pdpp-connector-feasibility-2026-09-24.md)). Today's Meta profile names `https://registry.pdpp.dev/connectors/meta`, with streams `profile`, `posts`, `post_likes`, `following`, and `ads` ([`manifest.json`](</home/tnunamak/code/data-connectors/connectors/meta/manifest.json>) lines 3–6, 31 onward). Unity's retained local Instagram declaration names `https://registry.pdpp.dev/connectors/instagram` and has only `profile` and `posts`, where `posts` is **one snapshot record** containing a `posts` array, not Meta's one record per post ([`pdpp-source-declarations.ts`](</home/tnunamak/code/unity-surfaces/packages/app-runtime/src/sources/pdpp-source-declarations.ts>) lines 1045–1118, 1448–1468). Its version is `0.1.0-local`; current Meta checkout is `0.3.3`, while the memo's copied artifact is `0.4.0` ([`meta.collection-profile-0.4.0.json`](evidence/meta.collection-profile-0.4.0.json) line 6). The current annotator requires exact source ID and manifest-version equality, then a retained stream mapping ([`pdpp-collection-profile-ingest.ts`](</home/tnunamak/code/unity-surfaces/packages/app-runtime/src/sources/pdpp-collection-profile-ingest.ts>) lines 173–242). It would refuse Meta before records are considered.

**Correction:** Do not treat labels or a source-ID alias as declaration equivalence. Specify the exact Meta SourceDeclaration revision(s), stream-to-Personal-Server scope mapping, and migration of legacy `instagram.posts` snapshot semantics. Keep existing Instagram data and grants under their current identity unless an explicit authorization/data migration is designed. Prove destination acceptance for a published, digest-pinned artifact, rather than a copied local profile. The corpus already flags exact live-grant revision admission ([research entry](</home/tnunamak/code/dotfiles/ai/research/connector-architecture/a-connector-artifact-should-embed-the-exact-declaration-revisions-it-fulfills-and-gate-each-run-on-the-revisions-live-grants-hold.md>)). Confidence: high.

### P1 — “Adapt the annotator into the Mobile owner-data commit flow” skips the actual destination contract

Mobile currently calls `toOwnerDataBody` and `writeScope` once per nonempty scope ([`owner-data-ingest.ts`](</home/tnunamak/code/unity-surfaces/apps/mobile/src/features/personal-server/owner-data-ingest.ts>) lines 163–215). That writer creates an encrypted data-file envelope, publishes it to storage, and advances an on-chain scope version ([`owner-data-client.ts`](</home/tnunamak/code/unity-surfaces/packages/owner-data-client/src/owner-data-client.ts>) lines 185–224). Desktop's PDPP path instead posts **each** `$pdpp` record to Personal Server `/v1/data/:scope` ([`collectionProfilePdppIngest.ts`](</home/tnunamak/code/unity-surfaces/apps/desktop/src/services/collectionProfilePdppIngest.ts>) lines 1–27, 105–185). Merely adding `$pdpp` to a Mobile `writeScope` body is not evidence that the PDPP importer receives or validates it. Calling `writeScope` per record would also change the current one-version-per-scope write and retry semantics. The decision acknowledges separate ingestion but understates this transport and storage fork ([decision, lines 26–29, 78, 92](mobile-pdpp-connector-feasibility-2026-09-24.md)).

**Correction:** Choose and prove the Mobile PDPP destination first: an owner-authorized Personal Server import that accepts one record per envelope, or a specified and tested translation from owner-data scope versions into PDPP records. Keep legacy writes for unmigrated scopes. Define partial-record failure, idempotency, retry, and whether a DCR scope is served from the legacy head or PDPP records. Confidence: high about the current fork; medium about which destination design is best.

### P1 — Admission and DCR completion gates need a stricter order

The memo puts declaration-aware admission before the dual-target collector and ingest ([decision, lines 75–82](mobile-pdpp-connector-feasibility-2026-09-24.md)). If this becomes active admission for an existing Mobile scope, it can refuse valid legacy connections or DCR continuations before a compatible Meta declaration and destination exist. A PDPP grant is bound to a concrete SourceDeclaration revision, and the indexed research recommends admitting a run only when the artifact fulfills **every** live revision held by still-servable grants; a mapping of requested Mobile scope names alone is insufficient ([research entry](</home/tnunamak/code/dotfiles/ai/research/connector-architecture/a-connector-artifact-should-embed-the-exact-declaration-revisions-it-fulfills-and-gate-each-run-on-the-revisions-live-grants-hold.md>)). The current DCR contract requires one prepared execution under the continuation lease, every approved scope delivered in approval order, and acknowledgement only after all reads succeed ([`mobile-hosted-connectors-migration.md`](</home/tnunamak/code/unity-surfaces/docs/cutover/mobile-hosted-connectors-migration.md>) lines 65–83, 337–341, 473–486). Mobile's ordinary run reports completion if **any** scope wrote, explicitly allowing partial results ([`connect_run.dart`](</home/tnunamak/code/unity-surfaces/apps/mobile-shell/lib/connect/connect_run.dart>) lines 423–449); that verdict cannot be reused as a DCR acknowledgement or PDPP full-coverage signal.

**Correction:** Make declaration checks shadow-only while legacy execution remains active. At pilot cutover, gate *before* execution on the exact prepared artifact, declaration revision(s), live grants, requested scopes, and supported host capabilities. Keep the prepared bytes and mapping fixed through the continuation. Gate DCR completion separately on confirmed writes and reads of every approved scope; leave partial delivery unacknowledged and retryable. Preserve owner binding and per-owner browser profile throughout. Confidence: high.

### P2 — Apple agreement citation is wrong; policy conclusion is appropriately cautious

The memo and indexed policy note cite Apple Developer Program License Agreement **§3.3.2** for interpreted code ([decision, lines 99–105](mobile-pdpp-connector-feasibility-2026-09-24.md); [research entry](</home/tnunamak/code/dotfiles/ai/research/mobile-runtime/mobile-webview-javascript-bridges-have-platform-and-store-policy-boundaries.md>)). In the current [agreement](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/), interpreted code is **§3.3.1(B)** and extra functionality is **§3.3.1(C)**; §3.3.2 is regulatory compliance. [App Review Guideline 2.5.2](https://developer.apple.com/app-store/review/guidelines/) contains the feature-changing-code restriction. [Google Play's policy](https://support.google.com/googleplay/android-developer/answer/16559646) does state a WebView-JavaScript exception to its downloadable executable-code restriction and a separate runtime-loaded-interpreter compliance rule. The memo correctly stops short of promising store acceptance. Correct the section reference and avoid describing Google's exception as blanket approval of hosted connectors. Confidence: high.

## Off-device OCI verification

Yes, off-device verification is feasible **under the already accepted Mobile-origin trust model**. A controlled release job can verify the OCI digest, expected signing identity and transparency evidence, build the PageShim artifact from the verified input, record input/output digests and builder identity, and atomically publish immutable script bytes with the matching catalog. The device then trusts the selected deployment origin and its prepared script snapshot, as it does now ([migration plan](</home/tnunamak/code/unity-surfaces/docs/cutover/mobile-hosted-connectors-migration.md>) lines 12–19, 79–83, 295–303). This does **not** preserve an end-to-end guarantee that the device itself executed publisher-signed bytes: a compromised deployment origin could serve a different script. If independent signer authenticity is a requirement, Mobile must verify a signed/pinned release manifest or artifact digest at runtime; upstream CI verification alone cannot provide it. Keep this trust decision before shipping a PDPP-branded Mobile claim, even if implementation work runs independently. Confidence: high.

## Revised recommendation and sequence

1. **Reject direct B.** Current OCI artifacts contain a Node/Playwright program; neither the signed package nor a WebView supplies the required execution ABI. Reconsider B only for a purpose-built Mobile runtime, with its own capability and store review, not as an installation shortcut.
2. **Retain the current Mobile host and DCR path.** Keep same-origin hosted scripts, the native source allowlist, per-owner WebViews, the single execution lease, exact prepared script bytes, and the existing owner-data path for legacy scopes.
3. **Resolve the data contract before connector cutover.** Publish/retain exact Meta declarations, define ID/scope/record-shape migration from legacy Instagram, specify the owner-authorized PDPP destination, and test destination validation, legacy reads, live grants, and partial writes. Run new admission checks in shadow mode until these contracts exist.
4. **Run a narrow A pilot.** Share pure provider parsers and record builders; keep separate Desktop and Mobile collection loops. Prove Meta with the same captured responses, then a real account on iOS and Android. Promote more shared code only when it removes demonstrated duplication without weakening host capability control.
5. **Cut over one scope/source with explicit gates.** Pin artifact, transformed bundle, exact declaration revisions, and scope mapping; check live grants and capabilities before prepare; write and read under the correct owner; preserve the DCR callback and acknowledgement contract. Roll back by source without rewriting existing scope history.
6. **Choose artifact trust explicitly.** Off-device OCI verification is sufficient for the current deployment-origin trust root if the release controls above are enforced. Add device-side verification only if the product needs independence from that origin. Desktop stage 1 can proceed separately.

The memo's effort bands are directional only. The Meta source/declaration mismatch and Mobile destination fork are gating design work absent from the 1–3 and 1–2 week estimates; no measured implementation or device evidence supports those numbers.
