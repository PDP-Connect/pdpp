PDPP Principles  ·  v1.0  ·  Published 3 September 2026

The principles guiding PDPP

When an individual permits a service to use information held about them by another, the permission is commonly granted in general terms and recorded nowhere the individual can examine.

The choice is often between all of the information and none of it, and once given, the permission is rarely visible, rarely verifiable, and rarely reversible in practice. The party relying on the information carries the same uncertainty, since it holds no reliable record of what was consented to, for what purpose, or by whom. As more of daily life is mediated by systems that act on personal information, and as artificial intelligence increases what can be done with it, the absence of a specific, durable and enforceable account of what has been agreed has become a matter of general concern.

  1. 01Primacy of the individual.Decisions about how information concerning a person is shared and used should rest with that person.
  2. 02Specificity of access.Access to personal data should be defined in terms of what is shared, for what purpose, and for how long, rather than granted in general terms.
  3. 03A durable record.What has been agreed should be recorded in a form that can be examined afterwards by the individual concerned and by the parties relying on it.
  4. 04Enforcement by design.Agreed limits should be applied automatically to each request, rather than depending on the continuing good conduct of the parties.
  5. 05Reversibility.Ending an arrangement should be as straightforward as entering into one.
  6. 06Openness.The specification should be published openly, implementable by any party, and operable without dependence on any particular provider.

§7 Grant

Comment on §7 Permalink View source History 3 open issues

A grant is the immutable record of what the user approved. It is issued by the authorization server after the user has acted on a selection request, and it is the only artifact a resource server consults when deciding whether to answer a query.

7.1 Immutability

A grant MUST NOT be modified after issuance. Where the user wishes to change what an accessor may see, the authorization server MUST issue a new grant, and MUST NOT narrow or widen an existing one.

A grant MUST record the source declaration snapshot against which it was issued. A resource server MUST evaluate every request against that snapshot, not against the current declaration.

7.2 Access modes

Where access_mode is single_use, the resource server MUST refuse any request made after the first successful retrieval. Where it is continuous, the resource server MUST answer requests until the grant expires or is revoked, and SHOULD support incremental sync as described in §4.

7.3 Representation

A grant is represented as a JSON object. The example below is non-normative.

// non-normative example
{
  "grant_id": "grn_8f2c1a04",
  "client_id": "https://habitcoach.example/app",
  "source": { "id": "https://sleeptracker.example", "official": true },
  "purpose": "https://pdpp.dev/purpose/personalisation",
  "access_mode": "continuous",
  "streams": [
    {
      "stream": "sleep_sessions",
      "fields": ["sleep_score", "duration_min"],
      "range": { "from": "2026-06-01", "to": "2026-09-01" }
    }
  ],
  "declaration_snapshot": "sha256:4c1f...9ab2",
  "retention": { "max_days": 90, "on_expiry": "delete" },
  "issued_at": "2026-09-02T09:14:00Z",
  "expires_at": "2026-12-01T00:00:00Z"
}

7.4 Fields

FieldRequiredDescription
grant_idYesStable identifier, unique to the authorization server
purposeYesA URI from the purpose registry in Appendix A
access_modeYessingle_use or continuous
declaration_snapshotYesDigest of the source declaration the grant was issued against

Governance  ·  Consultation draft  ·  Revised 2 September 2026

Who runs this, and who decides

Two parts. Part A is how it runs from 15 October. Part B is how we propose it runs once there is an elected committee. Both are open for comment until 1 October: how to comment.

Four stages

Pre  ·  now, to 15 Oct

Public comment

The specification and Part A are frozen while people comment, the Principles are published, and you can sign now. This stage ends on 15 October.

Phase 1  ·  from 15 Oct

Launch

The maintainers run things. Supporters can sign, but nobody can be verified until the review committee is named.

Phase 2  ·  from Nov 2026

Interim

Five people, at least three with no connection to Vana or Open Data Labs, chosen on published criteria and not removable by the maintainers. They review every application for verified status in public and give a decision with reasons, which the maintainers act on. Verification opens at this point.

Phase 3  ·  from 2027

Full

Partners elect a five-seat steering committee, one organisation one vote, with the Chair elected directly. The steering committee is the only body that can change the specification or grant a status, and it does both by majority vote. It appoints a technical committee, which reviews every application and every proposed change in public and recommends. The Chair records the vote and merges. This starts at 100 Partners or on 15 October 2027, whichever comes first, and not before 15 April 2027. Full detail is in Part B of the governance document.

How decisions are made once the steering committee exists

Before the steering committee exists, the interim technical committee recommends and the maintainers merge on that recommendation with no discretion. The shape is the same; only the body that votes is missing.

Build with PDPP

Everything you need to build on PDPP is here: the specification, a reference server you can run today, and guidance for the parts people tend to get stuck on.

What are you building?

I hold data

Make a source

You have data, on a platform or in a connector, and you want apps to be able to ask for it with consent. You need to write a source declaration that validates against Core §5, then serve records through a Core §8 resource server.

Start with Core §4 and §5, then the declaration schema and the validator.

Core §5 →
I want data

Make an accessor

You are building an app or agent that needs someone's data. You ask for exactly what you need with a Core §6 selection request, receive a grant, and query within it. If you have done OAuth, this is OAuth with a stricter scope.

Start with Core §6 and §7, then the client example in the reference implementation.

Core §6 →
I run the server

Make an operator

You run the authorization server, the resource server, or both. Yours is the code that records the grant and refuses anything outside it. Core §8 is your interface contract and §9 is what the test suite will check.

Start by running the reference implementation, then read Core §8 against it.

Building an accessor

Which purpose code do I put in my request?

Every grant names a purpose from the registry. Most requests fit an existing code, and ai_training is the one that triggers a protocol-level consent step. If nothing fits you can propose one, and proposals are considered on a published cycle.

Any role

Core can't express the query I need. Now what?

Extension profiles add lexical search, aggregation and semantic query on top of Core without changing what Core means. Check whether one already covers your case before writing your own; an extension that weakens Core semantics is rejected.
