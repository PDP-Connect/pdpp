# PDPP does not promise connector containment today, and prior art says most ecosystems never do

**Status:** decision record, folding finished research into a permanent note. Written 2026-09-02. Ends with an open owner question — not a settled answer.

## What PDPP promises today: nothing normative

The spec is explicitly non-normative on connector isolation. `spec-core.md` lines 1558-1560 (as read against `origin/main` at `9202f6b0a`) say:

> "In the Collection Profile, connectors receive credentials via the INTERACTION channel. A malicious connector could exfiltrate credentials. Production deployments SHOULD mitigate this by sandboxing connector processes (restricting network egress), using connectors from trusted registries only, or having the runtime authenticate on behalf of the connector and pass only session tokens. A formal connector trust model is deferred."

Three things about that sentence matter for anyone building against it. It is `SHOULD`, not `MUST` — optional guidance, not a protocol requirement. It offers sandboxing as one of three interchangeable mitigations, not a chosen mechanism. And it says outright that the whole area is "deferred."

A full grep across every spec file (`spec-core.md`, `spec-architecture.md`, `spec-auth-design.md`, `spec-change-tracking.md`, `spec-collection-profile.md`, `spec-connector-ecosystem.md`, `spec-data-query-api.md`, `spec-deferred.md`, `spec-discovery-and-trust.md`, `spec-reference-implementation-examples.md`) for isolation-flavored terms found exactly one other hit, and it is a different concept: `spec-connector-ecosystem.md` lines 11-15 uses "process isolation" to explain why the browser runs behind a CDP WebSocket binding instead of a custom protocol message — an architecture note about keeping the browser out of the connector's own process, not a claim that the connector process itself is contained from reaching arbitrary network destinations.

No user-facing surface says anything different. A grep across `README.md`, `index.md`, `SECURITY.md`, `docs/positioning/`, `docs/community/`, `apps/site`, and `apps/console` for containment-flavored language found no hits that refer to connector process isolation. Every "sandbox" hit on the public site refers to the `/sandbox` demo surface (deterministic fictional data for pedagogical browsing), not connector containment. This full inventory is captured in `local/ISOLATION-PROMISE-SCOPE-0901.md` (gitignored research scratch, not tracked in this repo), sections 1 and 2.

## What the isolation layer actually gates today: an offline dev tool, not live connector spawns

There is a real, adversarially-reviewed isolation module in the codebase — `packages/polyfill-connectors/src/scenario/isolation.ts`, built and hardened across six review rounds (R3 through R6) in late August 2026. It constructs Linux namespace closures (network, PID, mount, IPC, UTS) using bwrap/unshare, and its capability probe was hardened to catch a real bug where it once reported `available: true` while a namespace mount silently failed underneath it.

That module has never run on `origin/main` and has never been wired into the live connector-spawn path. Per `local/ISOLATION-PROMISE-SCOPE-0901.md` section 3, three independent checks confirm this:

- The file does not exist on `origin/main` at all — its history lives only on unmerged `waspflow/isolation-r*-0831` branches.
- Its only caller, on the branch where it exists, is `packages/polyfill-connectors/bin/scenario-verify.ts` — the offline half of a developer capture-then-replay loop. The property it proves is "did the fixture-replay tool leak to live egress while replaying a recorded scenario," not "can a real connector reach an arbitrary host service during a real run."
- A direct read of the live spawn site, `reference-implementation/runtime/index.ts:2308`, shows a plain `spawn(process.execPath, args, { detached: true, ... })` with no namespace flag, no `unshare`/`bwrap` invocation, no seccomp profile, and no network policy. `detached: true` exists only so the runtime can kill a connector and its descendants (Chromium, sidecars) as one process-group unit on cleanup — a lifecycle mechanism, not a security boundary. The surrounding code comment says plainly this is a Linux/Docker runtime with no Windows support.

Concretely, per that same document, section 4: nothing today stops a connector child process from opening a TCP connection to any host the parent server can reach, or a Unix socket anywhere the parent's filesystem permissions allow. A connector has exactly the reach the AS/RS server process itself has, minus nothing. If the whole server runs in one Docker container (the documented Core deployment shape), that container boundary — not a per-connector one — is the only thing a hostile connector descendant would need to cross.

This finding was independently confirmed twice: once by the red-team review of the Data Connect embed decision (`local/DC-EMBED-REDTEAM-0901.md`, Finding 1), and once by a second, independent grep/read pass in `local/ISOLATION-PROMISE-SCOPE-0901.md` that reached the same conclusion by a different method (direct spawn-site inspection rather than call-graph tracing).

Turning the existing namespace-construction primitive into a real production boundary would additionally require a DNS/proxy egress-allowlist broker that does not exist yet — a bare network namespace cannot express "reach only these hosts," and resolving names outside the policy while allowing the resolved IP through is a confused-deputy failure (per `local/ISOLATION-PROMISE-SCOPE-0901.md` section 5, itself citing the cross-platform-connector-runtime corpus file `02-cross-os-sandbox-guarantees.md`). That broker work has its own unreviewed risk surface and was not attempted by any of the sources this note draws on.

## What mature plugin/connector ecosystems actually do: trust by installation, not deny-by-default containment

`~/code/dotfiles/ai/research/cross-platform-connector-runtime/06-plugin-trust-models-prior-art.md` surveyed fifteen platforms — Airbyte, Singer/Meltano, Home Assistant, Terraform providers, GitHub Actions, Zapier/Make, VS Code extensions, Obsidian plugins, Backstage plugins, dbt packages, n8n nodes, Grafana plugins, and Docker/OCI runtimes — against a documented containment question: does a deny-by-default process/network boundary actually restrict what installed third-party code can reach.

The consistent finding: most of them do not. Obsidian says outright it "cannot reliably restrict plugin permissions" and that community plugins can access files, the internet, and install programs. n8n's own docs say community nodes have "full access to the machine and workflow data." VS Code desktop extensions run with the same permissions as VS Code itself — file, network, and process access — with the extension host acting as a stability boundary, not a security one. A separate process, container, or worker (Terraform's plugin subprocess, Grafana's backend plugin process) is common, but the research is explicit that a subprocess alone is "not containment" unless the platform documentation shows it also restricts filesystem, credentials, syscalls, and egress.

What these platforms use instead, layered together, is: publisher/namespace identity and official/partner/community tiers; review, acceptance tests, or catalog admission; signatures, checksums, lock files, commit pins, and increasingly provenance/attestation; declared permissions or scopes where the host can enforce them; and disable/revoke controls plus incident response. Real documented failures back this up rather than contradict it — Home Assistant's 2021 HACS directory-traversal disclosure, the 2025 `tj-actions/changed-files` GitHub Actions compromise, Zapier's 2025 npm supply-chain incident, and 2026 malicious npm packages impersonating n8n community nodes all happened inside platforms that were already using trust-by-installation, and none of the platforms' documented responses was "add a deny-by-default sandbox" — they tightened signing, pinning, and review instead.

Strong containment is reserved for a different threat model: browser extensions (adversarial web content, enforced by the browser process as reference monitor), mobile app sandboxes (mutually untrusted installed apps, OS-owned identity and permission brokers), and serverless customer-code runtimes like AWS Lambda (explicitly hostile or cross-tenant code, paid for with Firecracker microVMs). Docker/OCI sits in between — a real containment toolkit, but only when configured for it; default bridge networking still permits outbound internet, and the research is explicit that "containment available, not automatic" is the right characterization.

The research's own synthesis for a personal-data connector runner: curated first-party connectors can use trust-by-installation as the primary model (signed/pinned artifacts, explicit scopes, an out-of-process runner, narrow mounts, a recorded network allowlist), while community or arbitrary connectors need a real containment boundary — a rootless OCI runtime with no host-network mode, no broad host mounts, dropped capabilities, and proxy-mediated egress as a reasonable first step, with a VM/microVM reserved for actively-hostile code or a host holding unrelated secrets.

## What the wider cross-platform research implies for direction

The companion research in the same corpus reinforces why a uniform, VM-backed containment story is not a free move for PDPP specifically. `02-cross-os-sandbox-guarantees.md` establishes there is no portable native-process primitive with matching semantics across Linux, macOS, and Windows — Linux namespaces, macOS Seatbelt, and Windows AppContainer/LPAC each isolate different resources with different escape classes, and the only way to get one enforcement path across all three is to run a common Linux workload inside a VM. `03-bundled-vm-container-cost.md` shows that option is not a one-time cost: real products that ship this way (Docker Desktop, Podman Desktop, Rancher Desktop, Colima) all carry a permanent guest-image release-engineering surface — a 4-8 GiB RAM budget, 10-30 GiB disk, and an ongoing guest-OS update/rollback lifecycle. `04-browser-runtime-cross-os.md` adds that even a bundled VM doesn't buy a uniform product for PDPP's browser-driven connectors: headed-browser GPU support is not portable inside a VM either, so the same OS-specific escape hatch (a local GUI session or a remote CDP surface) is needed regardless of which isolation option is chosen.

Put together, the research supports a direction rather than dictates one: curated, pinned, signed first-party connectors as the primary trust model (matching what mature ecosystems do), with a real containment boundary — for example a rootless OCI runtime with no host-network mode, dropped capabilities, and proxy-mediated egress — reserved for community or arbitrary connectors if PDPP ever admits them. This is consistent with, but does not itself decide, the Data Connect embed decision covered in `design-notes/data-connect-embed-and-reorg-2026-09-02.md`, which picked "Linux-full via native OS primitives, honestly degraded elsewhere" as the near-term embed-scoped path — a decision explicitly scoped to the embed's timeline, not a claim that the underlying trust-model question below has been answered.

## OPEN OWNER QUESTION — not decided, flagged plainly

**Does PDPP intend to promise containment of connector code at all — a live-path, per-connector network/filesystem isolation guarantee, on some timeline and to some platform-parity bar — or does isolation stay scoped to dev-verification-tool integrity (what `scenario-verify.ts` already does), with production trust resting on trust-by-installation the way most surveyed ecosystems operate?**

This has not been decided anywhere in the corpus this note draws on. `local/ISOLATION-PROMISE-SCOPE-0901.md` poses this exact question at its own end and explicitly declines to answer it, on the grounds that the spec, the docs, and every user-facing surface currently make no connector-isolation promise, and the one isolation mechanism that exists is unmerged dev tooling never wired into the live spawn path. Any embed or desktop-porting decision that treats the R3-R6 layer as reusable production containment is pricing unstarted work as free — see the red-team finding in `local/DC-EMBED-REDTEAM-0901.md` (Finding 1) for the same conclusion reached independently against the Data Connect embed plan specifically.
