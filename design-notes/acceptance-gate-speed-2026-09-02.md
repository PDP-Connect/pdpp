# The acceptance gate's 18m44s is real work, not setup overhead — and the Postgres leg's bottleneck was schema rebuild, now mostly fixed

**Status:** decision record, folding finished measurement and review into a permanent note. Written 2026-09-02. The Postgres template-cloning fix is reviewed and shippable; the full-profile before/after number is still an extrapolation, not a direct measurement.

## What was assumed versus what was measured

Before this work, there was no direct measurement of where `pnpm test-accounting:check` (the required-all acceptance gate, 16 required suite/profile pairs) actually spends its time. `local/GATE-TIMING-MEASUREMENT-0901.md` closes that gap with a real, end-to-end run against `origin/main` at `9202f6b0a`, timed from the runner's own per-suite progress log, not estimated.

The headline finding: **the required-all leg's total wall time was 1124 seconds (18m 44s), and there is no measurable inter-suite setup or teardown gap.** The scheduler-to-scheduler wall clock (first suite's start to last suite's start) was 1122.6s — within 1.4 seconds of the sum of the 16 suites' own self-reported durations. All of the gate's time lives inside the 16 measured suite executions themselves; nothing is lost to unaccounted-for setup between them. Fourteen of the sixteen suites have no `prepare` step at all and no meaningful per-suite bootstrap — their "setup" is just spawning `node --test`. The one suite with a `prepare` step (`site`, a spec-doc sync) measured 0.12s, negligible. No suite in this measurement provisions a fresh PostgreSQL container, runs migrations, or loads fixture data as a one-time setup step; the only database activity is per-file, inside one specific suite, and only when a Postgres URL is explicitly configured — which it was not in this baseline run.

This matters because it rules out a whole class of "shave the setup overhead" optimization before it's tried: there isn't a setup-overhead tax to shave at the suite level. The two suites that dominate the total — `ri-default/memory-default` at 652s (58% of the total) and `polyfill-connectors/default` at 326s (29%) — are, per the report, "inherent... real, product-relevant test execution," not overhead. The one incidental (as opposed to inherent) cost identified in the whole measurement is `ri-default`'s hardcoded file-concurrency cap of 2, unchanged regardless of the host's actual core count (this host had 24 idle cores and the runner still ran two files at a time) — flagged as the next lever if further speed is wanted, but not itself acted on by any of the work in this note.

## The Postgres leg's real bottleneck: schema rebuild, not container start or fixture load

The optional Postgres profile (`ri-default/postgres`) was not run live in the timing measurement above — a port collision with a concurrent sibling investigation prevented it — so its cost was documented separately, from the code that would execute it, in `local/GATE-POSTGRES-PROVISIONING-0901.md`.

The finding there overturns a natural assumption. The gate does **not** spend its time on container startup (the Postgres container is long-lived, started once for the whole run) or on loading fixture data (most files seed a handful of rows after bootstrap, single-digit milliseconds). It spends its time **re-running roughly 1,960 lines of schema-bootstrap DDL and about 20 migration functions from scratch, via individual Postgres round-trips, once per test file — and again once per `test()` block in files that provision their own database directly**, which is most of them.

Measured directly on a representative, real, currently-passing test file (`connector-summary-fold-fleet-scope-contamination.test.ts`, 3 independent test blocks, each provisioning its own database): the schema-bootstrap DDL block (77 `CREATE TABLE` statements plus 91 `CREATE INDEX` statements) accounted for roughly 70-85% of a single provisioning cycle's cost, with the migration functions adding another 10-15%. Wrapping the DDL block in an explicit transaction was tested and found not to meaningfully reduce the index-creation cost — the report calls this "the one surprising negative result" — so the cost is the fixed work of building 91 index relations from scratch, not a batching or fsync problem that a transaction wrap would fix.

## The fix: `CREATE DATABASE ... TEMPLATE`, and what was proven unchanged

The recommended and later implemented fix uses Postgres's native template-cloning mechanism: build the schema once per gate run, mark that database as a template, and have every subsequent per-file or per-test database clone from it via `CREATE DATABASE ... TEMPLATE <name>` instead of running the DDL fresh each time. This is a byte-level filesystem copy of the already-built schema, not a re-execution of the DDL.

`local/GATE-POSTGRES-PROVISIONING-0901.md`'s prototype measured this on the same representative test file: **12.7s baseline, down to 2.6s steady-state with template cloning — an approximately 80% reduction on that one file**, with identical 3/3 pass results and identical assertions both times.

The implementation was then independently reviewed — not just re-read — in `local/GATE-SPEED-REVIEW-0902.md`, against commit `a932674f8` on the `waspflow/gate-speed-implement-0901` branch. The review deliberately did not trust the maker's own claimed 66% speedup number or a referenced evidence file that turned out not to exist (flagged explicitly in the review as a process gap: a gitignored evidence file was apparently written to a scratch worktree that was reaped before being copied out — a reminder that gitignored evidence must be copied to a durable location before a lane is torn down, not after). Instead the review reconstructed every claim from scratch on disposable infrastructure, using a different 6-file test subset chosen independently of the maker's own showcase file.

What the independent review proved, directly rather than by inference:

- **Equivalence**: the same 38 tests, byte-identical pass/fail events, on both the pre-fix and post-fix code, across an independently-chosen file subset.
- **Isolation unchanged**: the naming-grammar test (6/6 pass) and the fail-closed admission guard's own 9-case proof suite (9/9 pass) both pass unmodified, and a `git diff --stat` confirms neither file is touched by the fix's diff. The review also ran an active cross-clone leak attempt — writing a distinct marker row into two concurrently-cloned databases and confirming neither saw the other's write, with the source template itself kept non-connectable throughout — which the maker had not attempted.
- **Concurrency**, which the maker's own investigation had explicitly flagged as untested: the review ran the same 6-file subset with `PDPP_TEST_CONCURRENCY=6`, exercising the template's advisory-lock-guarded build-once/others-wait path for real, with a clean pass and no orphaned databases.
- **Fail-loud behavior**: forced three separate failure conditions (a nonexistent template name, a real database that was never marked as a template, and an end-to-end run through a real child test process with a bogus template name) and confirmed each one throws immediately, with no silent fallback to a from-scratch bootstrap and no silent pass against a stale or wrong schema. The review calls this "the single most safety-critical claim in the diff," and it held under direct, adversarial testing.

**The measured speedup, honestly reported as short of the maker's number**: the review's own paired, clean measurement showed **117.46s to 56.75s, a 51.7% reduction** on its independently-chosen 6-file subset — short of the maker's claimed 66% (on a different 5-file sample). The review attributes the gap to a different file mix (its subset includes a test with real Postgres query-planning cost that templating cannot remove) and to host contention during the review's own run (other concurrent sessions on the same shared host). Both numbers point the same direction and land in the same rough range (roughly 50-65% reduction); the review explicitly declines to reconcile them upward and states that neither number should be quoted as *the* figure for the full ~150-178-file Postgres leg, because **neither the maker nor the review ran the full profile end to end** — both numbers are subset-based, and the full-profile reduction is stated as "a reasonable but unverified inference," not a direct measurement.

## What the next bottleneck is now

With provisioning largely solved, the review measured where the remaining time on its 6-file/38-test subset actually goes: a one-time template build (3.70s, paid once per run), per-database clone and drop (roughly 0.1-0.2s each, steady state), and per-database schema initialization now running as fast no-ops against an already-cloned schema (0.35s). Summing these, the whole provisioning-and-teardown cost across the subset's roughly 8 clone/drop/init cycles comes to about 9.3 seconds — out of a 56.75-second total. **The other roughly 47 seconds is not provisioning at all; it is genuine PostgreSQL-backed test-body execution** — real `EXPLAIN`-plan assertions, real seeded-record round-trips against fault/resume matrices, work that exists with or without templating because it is the product doing real work against a real database.

The review explicitly draws the parallel to the earlier timing measurement's finding for the `ri-default/memory-default` leg: once the artificial overhead is removed, what's left is inherent, product-relevant execution time, which is the correct place for the remaining time to live. The one concrete lever the review points to with confidence for further speed, without having measured its effect, is the same fixed file-concurrency cap of 2 already flagged in the timing measurement — raising it is not blocked by anything the review found (template cloning was proven to survive `PDPP_TEST_CONCURRENCY=6` cleanly), but quantifying the win from raising it was explicitly out of scope for this review and was not done.

## What is unsafe for a certification-grade gate

`~/code/dotfiles/ai/research/testing/certification-grade-test-matrix-speed-2026-09-01.md` surveys how build-caching, test-impact analysis, and database-provisioning speedups interact with certification-grade evidentiary standards (DO-178C for airborne software, IEC 62304 for medical device software, SLSA/in-toto provenance attestation), and is explicit about what is safe, what needs pairing with a full-run cadence, and what is unsafe outright. The distinctions matter for reading the Postgres fix correctly and for any future speed work on this gate.

**Database-template cloning specifically is called out as safe to rely on directly**, and for a reason worth stating precisely: it caches *setup*, not *verdict*. The actual test logic still executes fresh against a real, isolated database every time; nothing about the test result itself is cached or reused. This is different in kind from the other techniques the research surveys, and it is why the Postgres fix above does not inherit the certification risk described below.

By contrast, the research names three things as **unsafe outright** for a certification-grade gate, none of which describe the Postgres fix, but all of which are worth keeping in view for any future gate-speed work on this codebase:

- **Treating a static-import-graph test selector's "no related tests found" as proof of no impact.** A companion research entry (cited in the same file) already established that Jest/Vitest/Playwright-class test-impact selection is static-import-graph-based, not execution-observed, and has documented blind spots around dynamic imports, fixture-file reads, and reflection.
- **Presenting a cached CI green as certification evidence without stating what it was cached against.** DO-178C's own text is explicit that the existence of evidence does not make it sufficient evidence — a cached pass from a build against a different compiler, target, or toolchain version is not creditable evidence for the artifact being certified now, regardless of whether the source hash matches.
- **Trusting a shared, unauthenticated remote cache across a trust boundary** — a PR-triggered build writing to the same cache namespace a protected-branch or release build later reads from. The research cites this as a proven, CVE'd vulnerability class (CVE-2025-36852, "CREEP"), not a theoretical risk.

The research also flags two things as **usable only when paired with a periodic full-run cadence and an explicit conservative fallback**: content-hash build/task caching (Bazel, Turborepo, Nx-class tools) and test-impact analysis of the Google-TAP or Microsoft-TIA kind. Both vendors' own published practice already assumes a full-run safety net is mandatory — Microsoft's own documentation recommends running the full suite in parallel and diffing against the selected-subset result specifically to *establish trust* in the selector, not as a one-time validation. Neither of these techniques is what the Postgres template fix does, and the research is explicit that its own confidence in the certification-grade template-cloning claim rests on exactly that distinction: setup-caching, not verdict-caching or selection.

Where the research says its own evidence is thin, that caveat carries forward here rather than being upgraded: it found no named-company, public-postmortem case of a test-impact-analysis decision (as distinct from a build-cache decision) directly causing a shipped defect, and IEC 62304's current edition does not, as far as the research found, contain a citable clause authorizing reduced-retest-scope credit for a cached or selected result — that appears to be coming in a future edition, not something the current standard already sanctions.
